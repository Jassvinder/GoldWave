## Core Principle

**Never trust client-side input. Validate and authorize everything on the server.** Client-side validation is for fast user feedback and UX only; it is never a substitute for server-side enforcement.

## Payment & Financial Safety (security-relevant business rules)

- **No refunds/reversals anywhere in the application.** Once a payment is confirmed, it is final. Corrections are represented only via a controlled reversal/correction ledger transaction with an audit trail — the application must not expose any endpoint or UI action that reverses a confirmed payment. (`DOMAIN_LOGIC.md` §0)
- **Idempotency is a security control, not just a correctness one.** Duplicate payment webhooks, retried callbacks, and re-run scheduled jobs must be rejected/no-op'd server-side so they cannot be used to duplicate income, payouts, or store-wallet credits. (`DOMAIN_LOGIC.md` §0, §19)
- **Members can never self-pay from the wallet.** A member may only submit a payout _request_; the request itself does not debit or transfer funds. Only Super Admin processing creates the actual debit. (`DOMAIN_LOGIC.md` §11)
- **Store Wallet deductions are atomic and balance-checked server-side before confirmation** — a store transaction must never be confirmed against insufficient wallet balance, and the balance check must not be race-condition-able by concurrent requests. (`DOMAIN_LOGIC.md` §16.1)
- **Draw winner selection uses a secure random-selection mechanism** with an auditable record; the client-visible slot-machine animation is cosmetic only and must never be able to influence or reveal the winner before the backend result is finalized. (`DOMAIN_LOGIC.md` §8.4)

## Sensitive Data Handled by This Application

- KYC-adjacent documents: PAN Card, Aadhaar Card, Bank Account Details, Passbook/Cancelled Cheque, Address, Profile Photo.
- Financial data: wallet balances, income/compensation history, payout bank details, store wallet balances/ledgers.
- These fields lock after one-time member submission; any change goes through the Super Admin-reviewed Change Request workflow, which preserves an old-value/new-value audit trail. (`DOMAIN_LOGIC.md` §13)

## Security Decisions and Risks

- **Accepted risk (by design, not a gap):** no payment refund/reversal capability exists anywhere in the app — this is an explicit business decision, not a missing feature. Do not add one without an explicit, documented client decision.
- **Open risk:** production launch requires legal/tax/KYC-AML/payout/product-valuation/regulatory review that has not yet happened — do not treat this document as a compliance sign-off.

Never place secrets, security bypass instructions, or exploit details in this file.
