# Task Tracker

Track only approved, actionable work. [TBD] must never appear as a task title.

## Rules

- Each task needs a stable ID, concise outcome, status, and dependencies when relevant.
- Status is exactly: Current, Pending, Blocked, or Completed.
- Before starting, check for duplicates and dependencies. On completion, move the item to Completed with date in DD-MM-YYYY format and a verification note.
- Do not create empty replacement tasks. Add a task only when real work is agreed or discovered.

## Entry Format

- [ ] **T-001 — Outcome** · Status: Pending · Depends on: none
- [x] **T-001 — Outcome** · Completed: 25-08-2026 · Verified: command or QA

## Testing Task Format

Use this pattern for a task whose outcome is verifying already-built work (a manual/UI QA pass, a regression sweep, a batched re-test across several modules) rather than building something new. It stays in the same T-0XX ID sequence and the same Current/Pending/Blocked/Completed lifecycle as every other task — no separate numbering, no separate file — only the body shape differs: the outcome names the pass and its scope, and each concrete thing to check is its own checkbox sub-item so partial progress is visible mid-pass.

On completion, move the whole entry to Completed per the normal Rules above — date in DD-MM-YYYY, plus a verification note. If a sub-item fails, do not check it off silently: note what was found and whether it was fixed in this same pass or spun off as its own new task, then check it off once actually resolved.
